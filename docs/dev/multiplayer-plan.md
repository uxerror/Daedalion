# Daedalion 1.4 multiplayer implementation plan

**Status:** Approved direction (maintainer decisions recorded in section 0). Stage briefs are written per stage.

## 0. Maintainer decisions (2026-11-24)

| Topic | Decision |
|---|---|
| Movement | Server-authoritative movement, immediate local look, interpolated remote players. The API keeps an input-sequence/ack hook so client prediction can be added later. |
| Identity | Server-issued player ID; the client stores a key and proves possession on reconnect. A hook lets a game plug in its own account system. |
| Death | Individual respawn at a checkpoint with inventory kept. Games can override the policy. Offline keeps reload-after-death. |
| Death and respawn (2026-11-25) | A dead player sees a private death screen; its Respawn button unlocks after a server-configured delay (default 10 s). The player respawns at separately authored, level-scoped respawn points; a replaceable selection policy decides which one (the default picks among the enabled points of the player's current level, falling back to the level's player spawn). Games may replace the policy or the death screen freely. |
| Player damage (2026-11-25) | Player-versus-player damage is on by default and switchable in the server configuration (`friendly_fire`). |
| Quests | Shared world progression by default; personal scope opt-in per quest. |
| Levels | **Players travel independently.** The server keeps several levels live at the same time (one live instance per level, shared by every player in it). This replaces "one active level, party travels together" below. |
| Transport | ENet (UDP) only, direct address / LAN. NAT traversal, relay, browser transports and matchmaking are out of scope for 1.4. |

### Consequences of independent travel

- The server (dedicated or listen host) simulates every level that has at least one player in it, and keeps an emptied level live for a configurable grace period before checkpointing and unloading it (default 60 s).
- Each live level gets its own physics/navigation space: a level instance root under a `SubViewport` with `own_world_3d = true` (rendering disabled on the server and for levels the local player is not in). This prevents bodies, areas and raycasts of different levels from interacting.
- Everything that currently scans the whole tree must be scoped to the level instance: `get_nodes_in_group()` / `current_scene` / `CogitoPersistentId.get_level_root()` users (about 71 call sites in 33 addon files), the persist/destroyed-node registries, element and NPC queries, audio emitters, and spawners. This scoping is a prerequisite for networking and is added as stage **MP0b** (offline-safe: single-player has exactly one level instance and behaves as before).
- Network identity becomes `(world_id, level_key, cogito_id)`; every live message carries the level key and that level's epoch. Interest management starts with "same level instance" before distance.
- Clients load only the level their player is in. Travel is per player: leave level A (checkpoint the player, despawn from A), load B locally, server spawns the player at B's connector once both are ready. Group travel becomes an optional game policy.
- Saves capture every visited level; live levels are captured at the same server tick, unloaded ones come from their last checkpoint. A listen host renders only its own level; other live levels still simulate on the host.
- Quests stay world-wide (one ledger shared across levels).
- MP10 grows from L to XL; MP0b is L.

Build co-op around **one authoritative simulation of one active level**. A listen host runs that simulation and owns a local player. A dedicated server runs the same simulation with zero local players and continues when everyone disconnects. Clients send player intentions and receive world state, private player state and presentation events. Offline play keeps the 1.3 execution path. These choices implement the scope recorded in `docs/roadmap.md:7–11`.

The first implementation milestone should be a dedicated server with **two independently moving Advanced players and no camera, HUD or input device on the server**. A listen-host-only prototype would conceal several of the most expensive dependencies in this project.

Use a thin `CogitoNet` facade over Godot’s high-level multiplayer API. Game code should express “this actor tried to open this door” or “this container changed”. The facade owns transport setup, identity, routing and session lifetime.

| Engine facility verified in the installed reference | Decision |
|---|---|
| `MultiplayerAPI`, `SceneMultiplayer`, `OfflineMultiplayerPeer` | Use `SceneMultiplayer` for online RPC/scene replication. The default offline peer already reports server authority with ID 1. Expose an explicit session mode so offline, listen and dedicated are distinguishable. Offline installs no transport, synchronizers, snapshot timers, interest scans or command serialization. |
| `ENetMultiplayerPeer.create_server(port, max_clients, max_channels, in_bandwidth, out_bandwidth)`, `create_client()`, `set_bind_ip()` | Ship native UDP ENet first. The documented server default is 32 clients and the transport ceiling is **4095 remote clients**. Do not inherit 32 as a gameplay rule. Use dynamic registries and a game-configured admission limit. If omitted, request the adapter ceiling. Count the listen host as a player when applying a game’s limit. Report actual transport limits and startup errors. |
| `WebSocketMultiplayerPeer`, `WebRTCMultiplayerPeer` | Accept a transport factory so a game can add either later. WebSocket’s reliable ordered stream changes movement latency under loss. WebRTC requires peer connections, signaling and ICE. Native ENet is the supported 1.4 transport. Browser transport, NAT traversal, matchmaking, hosted relay and host migration are outside the 1.4 deliverable. Provide LAN/direct-address join and document UDP forwarding for internet listen hosts. |
| `MultiplayerSpawner.spawn_path`, `spawn_function`, `spawn(data)`, `spawn_limit` | Use server-owned spawners. A custom spawn factory returns a detached node on every peer. The spawner attaches it. Configure identity and role before readiness. Keep `spawn_limit = 0` for the player spawner and enforce admission separately. Despawn through the authority’s node lifecycle. |
| `MultiplayerSynchronizer`, `SceneReplicationConfig` | Use primitive spawn properties, `REPLICATION_MODE_ON_CHANGE` for reliable changed state and `REPLICATION_MODE_ALWAYS` for expendable snapshots. Configure `replication_interval` and `delta_interval`. Objects, Resources, RIDs and instance IDs are unsuitable as synchronized properties. Use `public_visibility`, `set_visibility_for()`, filters and `update_visibility()`. Spawner-managed visibility can spawn/despawn its root. Authored level nodes need explicit baseline and visibility handling. |
| `@rpc`, `rpc_id()`, `get_remote_sender_id()`, `set_multiplayer_authority()` | Put RPCs on a stable, identically named session endpoint. Declare mode, local behavior, transfer mode and channel explicitly. Requests use `any_peer` and target server ID 1. Server messages use `authority`. Capture the sender before `await`. | `SceneTree.set_multiplayer(api, root_path)`, `multiplayer_poll`, `MultiplayerAPI.poll()` | Sibling subtrees can use separate APIs. Install each API **before** replication children become ready. | Headless export | Installed `--help` confirms `--headless` selects headless display and Dummy audio. Verify the actual feature tag and stripped content on an exported artifact in MP11. |

### Players, authority and movement

- **Role and identity.** Keep `peer_id` for one connection, `player_id` for one durable player record in a world and `entity_id` for one live avatar. A respawn may replace the avatar. A reconnect may change both peer and avatar. The server binds an authenticated identity to a peer before spawning. Default to a server-issued opaque player ID bound to proof of possession of a client key, with a fresh challenge on reconnect. Games can supply an account provider. A display name, claimed ID or save filename grants no ownership. Reject a second live login by default.
- **Spawn.** Load the level, index authored objects, authenticate, select a clear spawn/connector position, create the authoritative player, restore its record or grant starter items once, then enable replication and input. A listen host takes this same path locally. Dedicated starts with an empty roster. Give each spawned player a stable network node name and private inventory/attribute instances. On disconnect clear input, holds, seats, carry and container sessions, capture the player, then despawn.
- **Movement.** The local controller samples normalized movement axes, body yaw, aim pitch, held buttons and numbered action edges. The server consumes bounded commands at fixed physics ticks and acknowledges the last sequence in its snapshots. Send recent edges redundantly and consume each once. Expire stale input to neutral. Drive Advanced’s locomotion, collision, stairs, swim, climb, posture and push chart from these commands. A remote presentation rig interpolates between timestamped snapshots.
- **Prediction default.** Apply local look, crosshair and input feedback immediately. Ship authoritative translation with smoothing in 1.4. Full movement rollback would need reproducible chart timers, moving platforms, pushes, element locks, seat exits and animation-dependent transitions. The cost of the simpler default is visible movement latency at internet RTT. Expose input sequence, authoritative tick and acknowledged frame so a game can add bounded movement prediction and reconciliation. Teleports, respawns and level changes clear interpolation history.
- **Local menus.** Opening inventory, a readable, a keypad, the wheel, pause or death UI affects one player. A menu sends neutral movement and releases held actions. World time continues. Death releases owned interactions and opens only the victim’s UI. Default respawn is server-approved at a game-selected safe checkpoint with retained inventory. Keep offline reload-after-death behavior.

### Entity identity, commands and effects

Use `(world_id, level_id, cogito_id)` for persistent entities and append a stable relative component key where needed. Use server-minted, lifetime-scoped IDs for ephemeral projectiles and effects. Every live message includes a level epoch. Index identity to live node in both directions. Reject duplicate authored IDs at level load. Use game-defined stable level keys so equal root names in different scenes cannot collide.

Authored objects exist on both sides from the same content build. The server sends their current state and removals, including `save_object_state` and relevant non-`Persist` components. Runtime drops, pickups, NPCs, ragdolls and projectiles use an allowlisted archetype ID and a server spawner. Preserve the original persistent ID across restore. Use a spawner at the required stable parent or carry a logical parent ID and resolve it after parent creation. A pooled projectile gets a fresh lifetime ID on every launch. Never send a scene path supplied by a client to `load()`.

**Example — opening a keyed door**

1. The owner’s targeting ray finds the door. `get_actions(actor)` builds the local prompt, including disabled choices.
2. The client sends `{epoch, request_id, entity_id, component_key, action_id, expected_revision}`. Use a reliable channel for discrete actions. The listen host calls the same validator with its already-bound identity.
3. The server resolves sender → player, verifies active epoch, target, reach/LOS, posture, action availability, inventory, lock and revision. It derives origin from the actor. A held action also has a server-observed start, release/cancel and minimum duration.
4. The server consumes the key and changes the door in one operation. A repeated request returns the previous result. Simultaneous requests serialize against the door and inventory revisions.
5. Interested observers receive door state. The owner receives the inventory delta and result. A live event can play the latch sound once. A late join receives the open pose and collision state silently.

Apply the same flow to context-menu actions, sensor triggers, damage-operated switches and programmatic interactions. Give author-defined actions stable keys and register accepted payloads per component. Execute a locally configured `Callable` only after authority has resolved the key. A client cannot nominate a method, grant itself a successful lockpick, or submit an arbitrary resulting state.

### Rates, interest and join-in-progress

Proposed starting values, subject to measurement: **60 Hz server physics, 30 Hz input packets, 20 Hz nearby player/active-body snapshots, 5 Hz distant moving entities, 100 ms remote interpolation**. Send sleeping bodies and durable state on change. Start with a configurable **64 KiB/s outbound steady-state target per client** and a separately metered join baseline. Collect bytes, visible entities, reliable backlog, server tick time and snapshot age.

Use channel 0 for session/control, channel 1 `unreliable_ordered` for fixed-shape input/motion streams, channel 2 `reliable` for discrete gameplay commands and results, and channel 3 `reliable` for chunked baselines. Use `unreliable` for discardable effects where ordering has no value. Configure matching channel capacity. `call_remote` plus a direct host dispatch keeps host execution single. Reserve `call_local` for deliberately shared presentation handlers with event deduplication. Reliable order applies **within** a channel. Epochs, revisions and acknowledgements establish dependencies across channels.

Index entities spatially. Recompute interest on cell changes or a coarse interval with a margin to prevent flicker. Always include the player’s own data, relevant holders/targets and shared quest/world summaries. A hidden room can burn and an unobserved NPC can die. On interest entry send current state, destruction records and dependencies before enabling the proxy.

For join or resync, capture baseline revision `R`, apply authored removals, spawn dependencies, then state and private player data. Buffer changes after `R`. Require a ready acknowledgement, drain newer revisions and then enable commands. Bound backlog and regenerate an obsolete baseline. This supports variable player counts without requiring every client to receive every transform. Capacity remains a measured property of the game, transport and machine.

## 4. Saves, travel and dedicated operation

### Multiplayer save layout

Keep the v2 data-only envelope. Add a distinct multiplayer slot layout under a separate save root. **Use flat files within each generation.** Current storage rejects nested directories and links while copying, and the codec currently recognizes player and scene roots. Adding a world kind, manifest-aware reader and verifier is explicit implementation work. `SceneManagement/cogito_slot_storage.gd:84–101,104–151,155–175`, `SceneManagement/save_codec.gd:4–8,19–28,38–65,82–91`, `SceneManagement/cogito_slot_files.gd:55–99,115–118`.

| Proposed file | Contents |
|---|---|
| `world.v2.json` | World ID, layout version, generation and committed tick, active level/connector, visited-level index, player record index, shared flags/quests/objectives, and game-owned shared state. An empty player index is valid. |
| `scene_<level-key>.v2.json` | Per-level authored ID manifest, live runtime entities and parents, object/component state, velocities, NPC state, attributes/elements and destruction records. Preserve existing in-place and legacy restoration rules. |
| `player_<opaque-id>.v2.json` | Controller state, last level and safe pose, inventory with stack aliases, quickslots, equipped item/ammo, attributes, currencies, actor elements, health/death and personal quest state. The server generates filesystem-safe IDs. |
| Optional preview | Listen host may supply a screenshot. Dedicated does not require one. Server generation time drives multiplayer load selection. |

Use the existing staging, verification, rename, rollback and recovery machinery. Capture an immutable world-plus-players snapshot at one server tick. Carry forward visited levels and disconnected profiles from the last committed generation. Verify the manifest, current level and all referenced player files before publication. Keep private credentials outside world saves.

Listen hosts initiate manual saves and own the shared slot. Dedicated restores the last complete generation before accepting players, autosaves dirty state every **60 seconds** by default, checkpoints disconnects and flushes on orderly shutdown. Serialize save, leave and travel through one writer. A departure retains its captured profile until commit succeeds. A reconnect during that window uses the newest authoritative record. On write failure keep the prior complete generation, report to the host/operator and retry dirty state. Enforce one writer per world directory.

Restore the world and global progression **once**. Rebuild entities/parents, apply scene attributes and deferred elements, then restore each player’s private state and bindings. Reconcile references after their targets exist. For a player who missed group travel, restore belongings and use the current level’s safe entry. Revalidate seats and release stale carry references. Reconnecting must never reset the party’s quests, duplicate starter items or replay death/loot. Current player restore invokes the global quest restore and the manager starts a fade, so neither path can be reused wholesale. `SceneManagement/cogito_player_state.gd:106–150`, `SceneManagement/cogito_player_persistence.gd:35–42`, `SceneManagement/cogito_scene_persistence.gd:30–36,133–148`, `tests/saves/player_restore_test.gd:84–126`.

Keep existing offline v2 and supported legacy `.res` loading. Offer an explicit **copy/import** of a compatible solo slot: move shared fields into the world record, assign its player data to the designated host profile, and preserve the source. On dedicated, an operator designates that profile before import. A malformed v2 file remains an error. The retired Simple controller retains its existing incompatibility. `docs/save-format.md:3–16,41–57,114–138`, `tests/saves/save_codec_test.gd:189,224,315`.

### Level travel

> Superseded by section 0: players travel independently and the server keeps several levels live. The single-level flow below remains the per-level procedure (prepare, checkpoint, epoch, readiness), applied to one player instead of the party.

Original proposal: support **one active simulated level per server** in 1.4. All connected players travel together. Visited inactive levels retain their saved state. Independent parties in multiple live levels would require partitioning scene roots, group scans, physics spaces, IDs and save ownership. Current scene and persistence contracts assume a single root. `SceneManagement/cogito_scene_manager.gd:53–61`, `SceneManagement/cogito_persistent_id.gd:98–105`, `SceneManagement/cogito_persist_nodes.gd:17–24`, `SceneManagement/loading_screen.gd:59–86`.

1. Authority validates the triggering actor/zone, acquires the transition guard, closes interactions and fixes an outgoing snapshot tick. Coalesce simultaneous triggers.
2. Prepare the target and checkpoint the outgoing world. If preparation or publication fails, keep the old world live, release the guard and report the error.
3. Announce the target level key and next epoch. Clients display a local fade/loading screen and acknowledge content readiness. Gate spawns and deltas until that peer has matching node paths.
4. Authority activates the destination, restores it once, places the group at collision-checked connector offsets and publishes the baseline. A late join waits on the current epoch. A slow client can time out and reconnect without holding the server indefinitely.
5. Resume each ready peer. Ignore old-epoch commands, spawns and acknowledgements. Preserve `save_temp_on_enter` ordering after placement. Current offline ordering and failure tests are at `SceneManagement/loading_screen.gd:79–93`, `tests/saves/transition_save_test.gd:20,57`.

## 6. Decisions and risks

| Decide by | Recommended default | Risk or sign-off criterion |
|---|---|---|
| MP0 | Native ENet, application-configured capacity, one local player per client, game-supplied identity-provider hook | A demo limit must never become a fixed-size roster, spawn limit or save format. Test a roster larger than the demo default. |
| MP0 | Key-bound persistent identity, one active login per identity, explicit world import ownership | Reconnect must survive a new peer ID and server restart. Decide how the game recovers a lost client credential. |
| MP1 | Server movement, immediate local look, interpolated bodies, optional future prediction | **MP1 is the riskiest stage.** Controller input, physics, camera, UI, chart callbacks and animation timing meet in the same prefab. Sign off on real Advanced movement on dedicated and at representative RTT before expanding gameplay coverage. |
| MP2–MP4 | Atomic world actions, actor-addressed UI, one carrier/seat occupant, revisioned shared containers | The main failure mode is a correct-looking visual with duplicated currency, damage or items. Acceptance must compare authoritative state and count side effects. |
| MP5–MP7 | Individual respawn, retained inventory, zone-based authoritative visibility, simulation continues outside interest | Games can override death penalties and stealth sampling. Listen and dedicated must agree on gameplay outcomes with rendering disabled. |
| MP8 | Shared quests by default, personal opt-in, explicit party inventory policy | Decide whether absent members’ items satisfy live objectives. Recommended default: count disconnected holdings for uniqueness, count connected eligible members for live possession objectives, preserve already completed objectives. |
| MP9 | One transactional generation, flat profile files, 60 s dirty autosave, checkpoint on leave, explicit solo import | MP9 has the highest data-loss impact. Require restart and fault-injection evidence for a world containing offline profiles before release. |
| MP10 | One active level and whole-party travel. A validated connector triggers travel by default, with a game hook for quorum or host approval. | Independent live levels require a later world-instance design. Slow loading and empty servers must not deadlock travel. |
| MP11 | Direct connections and operator-managed deployment for 1.4 | Publish tested player/entity counts, bandwidth and tick-time measurements with the test scene and hardware. The engine transport ceiling is not a promised playable capacity. |
